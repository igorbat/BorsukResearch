# Проблема Борсука и задача Лармана на булевом кубе

Код к работе о гипотезе Борсука для подмножеств булева куба и о задаче Лармана
для срезов постоянного веса. Здесь лежит ровно то, чем получены опубликованные
результаты:

* **гипотеза Борсука верна для любого подмножества вершин $\{0,1\}^n$ при
  $n = 10$ и $n = 11$** (разбиение на $n+1$ часть меньшего диаметра);
* **гипотеза Борсука верна для срезов постоянного веса при $n \leq 11$**
  (разбиение на $n$ частей).

Ранее для полного куба это было известно при $n \leq 9$.

Метод: вместо перебора самих подмножеств строится конечная **покрывающая
система** — семейство надмножеств, покрывающее с точностью до изометрии все
подмножества заданного диаметра, — и раскрашиваемость каждого её элемента
проверяется SAT-решателем.

## Что нужно

* компилятор с поддержкой C++17 (`g++` или `clang++`);
* [kissat](https://github.com/arminbiere/kissat) — собранный бинарник.

Больше ничего: ни CMake, ни внешних библиотек.

## Сборка

```bash
./build.sh
```

Все программы окажутся в `build/`. Если хочется собрать что-то одно, команды
тривиальны:

```bash
g++ -std=c++17 -O2 -Icube/include -o build/v2_n10k6_5 \
    cube/experiments/v2_n10k6_5.cpp cube/src/helpers.cpp

g++ -std=c++17 -O2 -Islices -pthread -o build/larman_perebor \
    slices/larman_perebor.cpp slices/sat.cpp
```

## Запуск

Каждая программа принимает два необязательных аргумента:

```
<программа> [путь к kissat] [рабочий каталог]
```

Рабочий каталог используется для временных CNF-файлов и результатов; он должен
существовать. Без аргументов подставляются пути автора, поэтому **при запуске у
себя аргументы надо передавать**:

```bash
mkdir -p work
./build/v2_n10k6_5 /path/to/kissat work
./build/larman_sweep /path/to/kissat work
```

## Структура

```
cube/          гипотеза Борсука для подмножеств {0,1}^n, n = 10, 11
  include/     bruteforce.h — перебор с отсечением, helpers.h — геометрия куба
  src/         helpers.cpp
  experiments/ 19 программ, по одной на подзадачу (см. ниже)
slices/        задача Лармана для срезов постоянного веса, n <= 11
  larman_sweep.cpp     ценз всех троек (n,k,d) при n-1 цветах
  larman_ncolors.cpp   те же тройки при пороге n
  larman_perebor.cpp   перебор для четырёх троек, не взятых одним вызовом
  larman_cnc.h         координатор + пул воркеров
  larman_dedup.h       стабилизатор стартового ребра в S_n
data/          результаты цензов по срезам (TSV)
RESULTS.md     опубликованные таблицы — с чем сверяться
```

### Куб: 19 подзадач

Имя программы соответствует строке таблицы в статье. Случаи $k \in \{2,4,8\}$
берутся напрямую; случай $k = 6$ разбит по максимальной клике графа диаметров,
классифицированной с точностью до изометрии:

| n | программы |
|---|---|
| 10 | `v2_n10k2`, `v2_n10k4`, `v2_n10k8`, и для $k=6$: `v2_n10k6_2` ($K_2$), `v2_n10k6_3` ($K_3$), `v2_n10k6_4_1`, `v2_n10k6_4_2` ($K_4$ двух типов), `v2_n10k6_5` ($K_5$) |
| 11 | `v2_n11k2`, `v2_n11k4`, `v2_n11k8`, и для $k=6$: `v2_n11k6_2`, `v2_n11k6_3`, `v2_n11k6_4_1..3` ($K_4$ трёх типов), `v2_n11k6_5_1..3` ($K_5$ трёх типов) |

Научные параметры каждой подзадачи — размерность, диаметр, стартовая клика,
запрещённые конструкции, размер порции и таймер решателя — зафиксированы прямо
в исходнике: это содержание опубликованной строки, а не настройка. Аргументами
выносятся только пути.

### Срезы

`larman_sweep` проходит все 125 троек $(n,k,d)$ при $n \leq 11$ (чётное $d$,
$0 < d \leq 2\min(k,n-k)$), пытаясь раскрасить покрышку в $n-1$ цвет. Что
раскрасилось в $n-1$, тем более раскрашивается в $n$, поэтому дальше идут только
остальные: `larman_ncolors` проверяет их при пороге $n$. Оставшиеся семь троек
(средние срезы при $d=6$) дополнением $k \mapsto n-k$ сводятся к четырём, для
которых и запускается `larman_perebor`.

## Как читать вывод

Кубические программы печатают карту `results` и карту пропусков. Ключи устроены
так:

| в выводе | смысл | в таблицах статьи |
|---|---|---|
| `1000 + s: c` | множество `base ∪ chunk ∪ tail` раскрасилось, поддерево закрыто; узел дал элемент покрывающей системы | **TLeaves** `s:c` |
| `s: c` | раскраска не нашлась, узел остался открыт и перебор продолжен ветвлением | **OLeaves** `s:c` |
| `already seen: a: c` | конфигурации, отсечённые как изометричные уже пройденным | **Skipped** |

**Осторожно с ключом у `already seen`.** TLeaves и OLeaves индексируются
размером всей конфигурации, а пропуски — размером надстройки над стартовой
кликой. Чтобы получить глубину, как в таблицах, к ключу надо прибавить размер
стартовой клики. Например, `v2_n10k4` (стартовая клика $K_2$) печатает
`already seen: 1: 98`, а в таблице это `Skipped 3:98`.

Признак успеха — пустая очередь в конце: значит для данной подзадачи построена
покрывающая система, все элементы которой раскрашиваются, и гипотеза для этого
случая доказана. Непустая очередь означала бы, что часть конфигураций осталась
неразрешённой.

Срезовые программы пишут TSV со столбцами `n k d verts edges colors status`, где
статус — `SAT` (раскрасилось), `UNSAT` (доказано, что не красится) или `TIMEOUT`
(за отведённое время не решилось — нужен полноценный перебор).

## Сколько это считает

Куб при $n \leq 11$ целиком укладывается примерно в два часа на одном ядре
3 GHz; самая тяжёлая подзадача — `v2_n11k6_5_1`, около 17 минут. Свип по срезам
— порядка часа, перебор четырёх оставшихся троек — около 8 минут. Времена
зависят от машины и версии решателя; таймауты подобраны с запасом, поэтому на
более медленной машине результат тот же, а не хуже.

## Воспроизводимость

Опубликованные числа собраны в [RESULTS.md](RESULTS.md) — с ними и надо
сверяться. Полные данные цензов по срезам лежат в `data/`.

Одна оговорка про решатель: таймаут трактуется как «не раскрашиваемо». Это
безопасно в том смысле, что может лишь увеличить дерево перебора, но не привести
к ложному выводу о доказанности — последний требует, чтобы каждая конфигурация
была разрешена положительно. Но на очень медленной машине или с другим
решателем дерево может оказаться крупнее, а времена — заметно больше.
